# С чего начать ArticleFlow

Этот файл объясняет смысл работы без формальных подробностей. Не пытайтесь сразу написать всё приложение. Собирайте его по этапам и после каждого этапа проверяйте небольшой пример.

## Что именно вы делаете

Вы пишете **локальную модель агрегатора статей**.

Приложение умеет:

1. обратиться к функции-источнику;
2. получить от неё сырые статьи;
3. привести статьи к единому формату;
4. сохранить их в каталоге;
5. найти статьи по тексту, источнику или тегу;
6. показать статистику;
7. перестать обращаться к источнику после нескольких ошибок.

Вам **не нужно парсить настоящий Хабр**, делать HTTP-запросы, читать JSON или создавать базу данных. Внешний сервис заменён обычной функцией.

```python
def fetch_habr():
    return [
        {
            "id": "habr-1",
            "title": "  Замыкания   в Python ",
            "text": "  Текст статьи. ",
            "tags": [" Python ", "Functions"],
            "rating": 42,
        }
    ]
```

Если сервис временно недоступен, функция возвращает `None`:

```python
def fetch_habr():
    return None
```

## Основные слова из условия

| Термин | Что он означает в этой работе |
|---|---|
| Источник | Функция без аргументов, которая возвращает список статей или `None` |
| Сырая статья | Словарь, который вернула функция-источник |
| Нормализованная статья | Новый словарь с очищенными заголовком, текстом и тегами |
| Каталог | Внутренний словарь приложения: `id статьи → статья` |
| Монитор | Набор функций, запоминающих успехи и последовательные ошибки источника |
| Команда | Внутренняя функция приложения: загрузить, найти, показать статистику и т. д. |
| Диспетчер `run` | Одна функция, через которую внешний код вызывает команды |
| Конвейер | Функция, последовательно запускающая несколько других функций |

## Как движутся данные

Когда выполняется:

```python
run("fetch", "habr")
```

происходит следующая цепочка:

```text
run получает команду "fetch"
        ↓
находит функцию fetch в словаре команд
        ↓
монитор проверяет, можно ли обращаться к habr
        ↓
вызывается sources["habr"]
        ↓
источник возвращает None или список сырых статей
        ↓
при успехе статьи проходят нормализацию
        ↓
статьи сохраняются в каталоге по id
        ↓
fetch возвращает короткий отчёт о загрузке
```

Главное: строка `"fetch"` сама ничего не загружает. Она используется как ключ, по которому диспетчер находит объект функции.

## Необходимые функции

В `article_aggregator.py` находятся четыре верхнеуровневые функции:

```python
create_article(...)
make_pipeline(...)
make_service_monitor(...)
build_application(...)
```

Они не являются четырьмя несвязанными задачами:

```text
build_application
    ├── создаёт monitor для каждого источника через make_service_monitor
    ├── создаёт конвейер через make_pipeline
    ├── нормализует записи через create_article
    ├── создаёт каталог
    ├── создаёт команды
    └── возвращает диспетчер run
```

## Этап 1. Научитесь создавать одну статью

Реализуйте `create_article`.

Вход:

```python
tags = [" Python ", "Functions", "python", "  "]

article = create_article(
    "a-1",
    "  Python   Functions ",
    "  Functions are objects.  ",
    source="habr",
    tags=tags,
    rating=10,
)
```

Ожидаемый результат:

```python
{
    "id": "a-1",
    "title": "Python Functions",
    "text": "Functions are objects.",
    "source": "habr",
    "tags": ["python", "functions"],
    "metadata": {"rating": 10},
}
```

Что здесь происходит:

- `"  Python   Functions "` превращается в `"Python Functions"`;
- одинаковые теги `" Python "` и `"python"` превращаются в один тег;
- пустой тег удаляется;
- `rating` попадает в `metadata`;
- исходный список `tags` остаётся неизменным.

Проверьте отдельно:

```python
first = create_article("1", "A", "B", source="test")
second = create_article("2", "C", "D", source="test")

first["tags"].append("changed")

print(first["tags"])   # ["changed"]
print(second["tags"])  # []
```

Если изменился и `second`, значит разные вызовы используют один список — это нужно исправить.

## Этап 2. Сделайте конвейер

`make_pipeline` получает функции и возвращает одну новую функцию.

```python
normalize = make_pipeline(
    str.strip,
    str.lower,
    lambda text: text + "!",
)

print(normalize("  PyThOn  "))
# python!
```

Алгоритм внутри будущей функции `pipeline`:

```text
result = исходное значение

для каждой функции:
    result = функция(result)

вернуть result
```

Если функций нет, цикл не выполнится и вернётся исходное значение.

Почему это замыкание: `make_pipeline` уже завершилась, но функция `pipeline` продолжает помнить переданный набор функций.

## Этап 3. Сделайте монитор одного источника

Монитор не загружает статьи. Он только считает результаты обращений.

```python
monitor = make_service_monitor(2)
```

Число `2` означает: после двух последовательных ошибок источник считается недоступным.

### Таблица изменения состояния

| Действие | Успехи | Все ошибки | Ошибки подряд | Можно вызывать |
|---|---:|---:|---:|:---:|
| Создали монитор | 0 | 0 | 0 | `True` |
| `record(False)` | 0 | 1 | 1 | `True` |
| `record(False)` | 0 | 2 | 2 | `False` |
| `record(True)` | 1 | 2 | 0 | `True` |
| `reset()` | 0 | 0 | 0 | `True` |

`successes`, `failures` и `consecutive_failures` должны быть локальными переменными функции `make_service_monitor`. Вложенные функции продолжают видеть их после завершения внешней функции.

Для изменения чисел из `record` и `reset` понадобится `nonlocal`.

Проверьте независимость:

```python
first = make_service_monitor(1)
second = make_service_monitor(1)

first["record"](False)

print(first["can_call"]())   # False
print(second["can_call"]())  # True
```

## Этап 4. Начните собирать приложение

Только после первых трёх этапов переходите к `build_application`.

В начале функции понадобятся три внутренних состояния:

```text
копия словаря источников
отдельный монитор для каждого источника
пустой каталог статей
```

Концептуальная структура функции:

```python
def build_application(sources, /, *, max_failures=3):
    # 1. Создать внутренние структуры.

    # 2. Определить вложенные команды:
    #    fetch, list_articles, search, stats,
    #    source_status, reset_source, available_commands.

    # 3. Собрать команды в словарь.

    # 4. Определить run(command, /, *args, **kwargs).

    # 5. Вернуть run.
```

Это схема, а не готовое решение. Весь каталог и все мониторы остаются внутри замыкания `run` и команд.

## Этап 5. Сначала реализуйте только `fetch` и `list`

Не пытайтесь сразу написать все команды.

Минимальный сценарий:

```python
def fetch_habr():
    return [
        {
            "id": "h-1",
            "title": "  Test   article ",
            "text": " Text ",
            "tags": [" Test "],
        }
    ]


run = build_application({"habr": fetch_habr})

print(run("fetch", "habr"))
print(run("list"))
```

Ожидается:

```python
{
    "status": "ok",
    "source": "habr",
    "received": 1,
    "added": 1,
    "updated": 0,
}
```

и список с одной нормализованной статьёй.

### Логика `fetch` простыми словами

```text
если монитор запрещает запрос:
    вернуть blocked

вызвать функцию источника

если источник вернул None:
    записать ошибку в монитор
    вернуть unavailable

иначе:
    записать успех
    нормализовать каждую статью
    добавить новую или обновить существующую
    вернуть статистику загрузки
```

`added` — сколько новых `id` появилось.  
`updated` — сколько уже существовавших `id` было заменено.  
`received` — сколько записей вернул источник.

## Этап 6. Добавьте остальные команды

| Команда | Что получает | Что возвращает |
|---|---|---|
| `fetch` | имя источника | отчёт о загрузке |
| `list` | ничего | копии всех статей |
| `search` | запрос и необязательные фильтры | копии подходящих статей |
| `stats` | ничего | число статей и статистику по источникам |
| `status` | имя источника | статус его монитора |
| `reset` | имя источника | статус после сброса |
| `commands` | ничего | tuple имён всех команд |

### Как работает диспетчер

Внутри приложения есть словарь:

```python
commands = {
    "fetch": fetch,
    "list": list_articles,
    # остальные команды
}
```

Диспетчер не должен самостоятельно выполнять логику каждой команды. Он только выбирает функцию и передаёт ей аргументы:

```text
найти commands[command]
вызвать найденную функцию с *args и **kwargs
вернуть результат
```

Поэтому `run("fetch", "habr")` концептуально превращается в `fetch("habr")`.

## Этап 7. Проверьте защиту состояния

Приложение хранит каталог внутри замыкания. Внешний код не должен менять его случайно.

```python
articles = run("list")
articles[0]["title"] = "Подмена"
articles[0]["tags"].append("fake")

print(run("list")[0])
```

Во внутреннем каталоге должны остаться исходные заголовок и теги.

Для статьи достаточно создать:

- новый внешний словарь;
- новый список `tags`;
- новый словарь `metadata`.

Полный `deepcopy` не требуется.

## Полный пример изменения состояния

Пусть `max_failures=2`, а источник по очереди возвращает:

```text
1-й вызов → None
2-й вызов → None
3-й вызов → список статей
```

Тогда приложение ведёт себя так:

| Команда | Вызывается ли источник | Результат |
|---|:---:|---|
| первый `fetch` | да | `unavailable` |
| второй `fetch` | да | `unavailable` |
| третий `fetch` | нет | `blocked` |
| `reset` | нет | монитор снова доступен |
| следующий `fetch` | да | `ok` и статьи добавлены |

Именно такой сценарий уже находится в `demo.py`.
